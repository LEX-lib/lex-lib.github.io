<objective>
Expand the proven tracer path into the boarder's full identity: assignable tags with a
vocabulary the admin extends in-app, and an optional link to an existing user account.

Purpose: TAG-01 is the requirement that forced `tags` to be a `json` string array rather than a
`select` field — PocketBase's Collections API is superuser-only at runtime, so an option list
that lives in the schema is unreachable to PayTime's admin and would make "add a tag" a code
change plus a deploy. This plan is where that decision either delivers or quietly regresses to
a hardcoded list. ROSTER-03's optional link is what makes the boarder — not the account — the
payment subject Phases 39–41 build on.

Output: the tag normalization contract with unit tests, the free-entry-behind-a-click tag
picker, tag chips on roster rows, the filtered account dropdown, and mapper payload tests.
</objective>

## UI-SPEC discrepancy, recorded not resolved silently

`38-UI-SPEC.md`'s E3 rows describe "no tags exist yet in `paytime_tags`", "PrimeVue's `loading`
prop while the tag list fetches" and "Tag-list fetch failure → toast 'Failed to load tags.'" —
all three presume a separate `paytime_tags` collection with its own fetch. **D-38-01 rejected a
tags collection outright**, and D-38-02 makes the vocabulary the union of tags already on roster
rows. None of the E3 considerations are dropped: each is preserved above and re-bound to the
roster read that actually supplies the option list, which produces the same observable states
(options unavailable while loading, a toast on failure, an empty-vocabulary message). The copy
"Failed to load tags." is replaced by the roster load toast because there is exactly one fetch
to fail, and two toasts for one failure would be a lie about what broke.

## Flagged planner assumptions (unresolved edge-probe rows)

Three edge-probe rows in this plan's scope came back `category: "unclassified"`. They are not
auto-backstopped and not dismissed — the assumption made in each case is recorded here:

- **ROSTER-02 (unclassified) — assumption:** "one or more tags" is assumed to mean an
  unordered set with no minimum. Zero tags is a valid, expected steady state (D-38-02 starts the
  vocabulary empty), tag order carries no meaning and is not preserved as authored — the stored
  array is de-duplicated and rendered in whatever order the array holds. No maximum tag count
  is enforced; a per-tag character bound is applied as input validation at the trust boundary.
- **ROSTER-03 (unclassified) — assumption:** "link to an existing user account" is assumed to
  mean exactly zero-or-one account per boarder, and at most one boarder per account (the
  D-38-10 unique index). Linking is assumed to be an admin action only, never inferred from a
  signup or an email match, and unlinking is assumed to be achieved by re-selecting
  "No account", not by a separate unlink action.
- **TAG-01 (unclassified) — assumption:** "without a code change or deploy" is assumed to be
  satisfied by data-resident vocabulary alone. Tag *retirement* and *rename-across-all-boarders*
  are assumed out of scope (CONTEXT.md records both as never discussed): with usage-derived
  options a tag disappears from the vocabulary once no boarder holds it, so retirement is
  implicit, and there is no bulk rename action.

mechanism, not a fallback — there is no seeded list in code, because a seeded list would
reintroduce exactly the code-change-to-edit problem D-38-01 exists to avoid. The vocabulary
starts empty and grows only from what the admin has already assigned.

wrapper (`flex-wrap` is what makes many chips wrap instead of clipping) containing one

`aria-label` naming the tag) that removes that entry from `tags`. Chips are `severity="info"`,
never the preset accent — the accent stays reserved for the Add Boarder button, the active
sub-tab indicator and focus rings.

Below the chips, a single (non-multiple) `AutoComplete` bound to `tagQuery` with
`:suggestions="tagSuggestions"`, `dropdown` off, a `completeMethod` handler, `fluid`, an
`inputId` of `pt-boarder-tags`, a label reading "Tags", a `placeholder` carrying an example so
the field is not a blank stare, and `emptySearchMessage` / empty-state copy
`No tags yet — type to create one.` The `completeMethod` computes, from the normalized query:
first every vocabulary entry that contains the normalized query as a substring and is not
already assigned, in vocabulary order; then, only when the normalized query is non-empty and
matches no vocabulary entry exactly and is not already assigned, one final sentinel entry whose
label is `Create tag: "…"` wrapping the typed text. The create entry is always last and is
never merged into a match row (D-38-03). Truncate the typed value inside the create label past
roughly 30 characters so a long paste cannot stretch the panel.

into `tags` — the sentinel's payload carries the normalized typed text — then clear `tagQuery`

create label.

spiked on this instance (D-38-05, permanent across Phase 38 and Phase 41), so no later phase
