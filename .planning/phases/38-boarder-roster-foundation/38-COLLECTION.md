## Indexes

One **unique** index, on the `user` field:

```sql
CREATE UNIQUE INDEX `idx_cI4xxZj3yh` ON `paytime_boarders` (`user`) WHERE `user` != ''
```

The index name was auto-generated by the Admin UI.

**The `WHERE user != ''` predicate is load-bearing, not decoration.** PocketBase stores an
unset `maxSelect: 1` relation as the empty string `''`, not SQL `NULL`. A plain
`UNIQUE(user)` would therefore treat every unlinked boarder as colliding with every other
unlinked boarder — the first would save and the second would be rejected. Making the index
partial excludes unlinked rows from the constraint entirely, so uniqueness applies only where
a link actually exists (D-38-10: one boarder per linked account).

This is the same idiom PocketBase itself uses in this instance for `users.email`:
`CREATE UNIQUE INDEX ... ON users (email) WHERE email != ''`.

## API rules

Verbatim, as configured:

- listRule:   `@request.auth.id != ""`
- viewRule:   `@request.auth.id != ""`
- createRule: `@request.auth.is_admin = true`
- updateRule: `@request.auth.is_admin = true`
- deleteRule: `@request.auth.is_admin = true`

Both traps named in the plan are confirmed avoided:

- **No rule is an empty string or `null`.** In PocketBase `""` means public unauthenticated
  access and `null` means superuser-only; every one of the five rules carries an explicit
  predicate (PITFALLS #4).
- **All three write rules contain the literal `is_admin`,** not the "is logged in" form
  `@request.auth.id != ""`. The one-token swap that shipped in `GiftExchangeManage.vue`
  (PITFALLS #1) is not present here.

Read/write asymmetry is intentional: any authenticated user may read the roster; only
`is_admin = true` may create, update or delete. Reads are all-or-nothing per row — PocketBase
has no field-level read restriction, so an authenticated non-admin can see every boarder's
`name`, `tags`, `user` and `is_active`.

## Deviations from the plan's stated schema

Two items in the plan's Task 1 spec could not be satisfied as written. Both are recorded here
rather than glossed, because Plan 38-03's grep gates and the Phase 38 verifier read this file.

### 1. `is_active` default `true` — not achievable at schema level

The plan (D-38-18) calls for `is_active` to be a bool with **default value `true`**. The live
field carries no default, and no Admin UI control exists to set one: **PocketBase v0.23+ removed
per-field default values.** Confirmed against this same instance — `users.is_admin` is a
non-system bool created earlier and likewise carries no `default` key. An absent bool reads
back as `false`.

**Consequence, and where it is enforced instead:** the default moves into application code.
`src/lib/pocketbase/paytimeBoarderMapper.ts` sends `is_active: true` explicitly in the create
payload rather than relying on the server, and read paths treat an absent or `false` value as
inactive. Any future write path that bypasses the mapper must set `is_active` itself — there is
no server-side backstop.

### 2. Two-unlinked-boarders probe — not run in the Admin UI

The plan asks for two throwaway rows (`probe-a`, `probe-b`) with `user` left empty, to confirm
both save, closing 38-RESEARCH.md assumption A1.

**Outcome: not run.** Verified by inspection rather than assumed — the collection holds
`totalItems: 0`, and the prod request log for `paytime_boarders` contains only four superuser
`GET`s (schema and record reads at 08:26, 09:12, 09:16, 09:16) with no `POST` or `DELETE`
against `/api/collections/paytime_boarders/records` at any point. The probe did not happen.
It also could not be run from the tooling side: the prod MCP environment grants `RecordRead`
but not `RecordCreate`.

**Why this is deferred rather than blocking.** A1 is what the partial index predicate above
directly encodes — `WHERE user != ''` removes unlinked rows from the uniqueness constraint by
construction, and the `users.email` index proves the idiom already works on this instance.
The empirical confirmation is folded into work that exercises the real path instead of a
superuser Admin UI shortcut:

- **Plan 38-01 Task 2** (tracer: admin adds a boarder by display name, no account link) adds
  **two** unlinked boarders during its in-app verification and records whether both saved.
  This is a stronger test than the Admin UI probe: it runs through the app as an ordinary
  `is_admin` user against the real `createRule`, not as a PB superuser bypassing rules.
- **Plan 38-03** runs the live unauthenticated-read (VERIFY-03) and admin-gated-write
  (ROSTER-06) probes against a seeded roster.

If two unlinked boarders do **not** both save in Task 2, stop — Plan 38-02's optional
account-link design (ROSTER-03) rests on A1 and would need revisiting before Wave 2 builds
on it.
