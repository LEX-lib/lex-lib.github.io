## The per-operation denial status map

Assert **per operation**. Asserting 404 on a denied create, or 400 on a denied update, makes the probe
itself look broken and is the easiest way to record a false result.

| Rule | Denial outcome |
|---|---|
| `listRule` | HTTP **200** with an empty items array and zero total — **not** an error. Every list case must cross-check against an identically-filtered admin-token count, or a denial reads as a pass. |
| `createRule` | HTTP **400** |
| `viewRule` / `updateRule` / `deleteRule` | HTTP **404** |
| any rule set to `null` (superuser-only) hit by a non-superuser | HTTP **403** |

**The app admin is not a PocketBase superuser.** It is an ordinary `users` row whose `is_admin` boolean
is true, so it IS subject to every collection rule — which is what makes the explicit admin branch
load-bearing rather than redundant. A sweep run with a true superuser session would pass even against
rules with no admin branch at all. Confirm which tier the supplied token belongs to before drawing any
conclusion from the admin half.

## Rule text hard constraints (carried invariants, non-negotiable)

- Never `""` — PocketBase treats empty-string as **public**, not "unconfigured".
- Never a bare `@request.auth.id != ""` as a write rule's only guard — satisfiable by *any*
  authenticated user (PITFALLS #1; the real `isSuperUser = isLoggedIn` bug in `GiftExchangeManage.vue`).
- Literal `is_admin` on **every** write branch, so SUBJ-06 holds without special-casing.
- `@request.body.` on createRule, **never** the deprecated `@request.data.` — the deprecated form 403s
  against this instance.
- A leading authenticated-caller conjunct on **all five** rules (T-39-14 — see must_haves).
- The `:isset` guard sits **outside** the admin OR-branch (D-39-07).
- All five authored and pasted back **together** (PITFALLS Pitfall 6).
