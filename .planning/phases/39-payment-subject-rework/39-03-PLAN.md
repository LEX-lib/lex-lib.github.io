<objective>
Close the phase's verification requirements in one autonomous pass: seed the second linked boarder,
sweep all five rules with both tokens in both directions, prove destructively that deleting an account
never destroys payment history, clean up every disposable row, and seal the evidence and security
artifacts.

Purpose: this collapses the original 39-05 and 39-06 and removes both of their human gates. The
original plans routed the seed through the Admin UI and the throwaway-account lifecycle through
superuser actions. Neither needs a human: linking an account to a boarder is a `PATCH` on
`paytime_boarders.user`, which the admin token is authorized for; and a throwaway account can be
created by signup and deleted with its own token. Both fall back to a checkpoint only if the live rules
actually refuse them.

Phase 38's executor had **no** credentials at all and had to resolve the base URL from a committed
`dist/` artifact — which is why ROSTER-06's authenticated-non-admin write half is still proven by rule
text only. Plan 39-02 supplied real tokens; this plan is where that gap finally closes.
</objective>

## The per-operation denial status map

| Rule | Denial outcome |
|---|---|
| `listRule` | HTTP **200** with an empty items array and zero total — **not** an error. This is the failure signature to watch for, and the reason every list case cross-checks against an admin-token count. |
| `createRule` | HTTP **400** |
| `viewRule` / `updateRule` / `deleteRule` | HTTP **404** |
| any rule set to `null` (superuser-only) hit by a non-superuser | HTTP **403** |

**The app admin is not a PocketBase superuser.** Ordinary `users` row, `is_admin` true, subject to every
collection rule. A sweep run with a true superuser session would pass even against rules with no admin
branch at all. Confirm the tier before drawing any conclusion from the admin half.

## The two outcomes the boarder-delete probe must tolerate

`39-RESEARCH.md` § 6 surfaced a LOW-confidence, unofficial report (GitHub issue #6498) that PocketBase
may **refuse** to delete a record referenced elsewhere by a `required: true` + `cascadeDelete: false`
relation, rather than succeeding and leaving an orphan. That is exactly the config
`paytime_payments.boarder` now carries. Official docs are silent either way.

| Branch | Observation | VERIFY-05 verdict |
|---|---|---|
| **ORPHANED** | The boarder delete returns 2xx; the payment survives with a `boarder` pointing at a now-nonexistent id | **PASS** — matches D-39-13/D-39-16's stated expectation |
| **REFUSED** | The boarder delete returns 4xx naming the required relation; both rows survive untouched | **PASS** — payment history survives by an even stronger mechanism than expected |

Do **not** write an acceptance criterion that only passes on one branch, and do not treat a 4xx delete
response as a test failure. Both satisfy VERIFY-05's real goal: no payment history is destroyed. Record
which one actually fired.
