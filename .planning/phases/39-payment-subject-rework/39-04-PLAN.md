## Final rule text — pick ONE branch from `39-COLLECTION.md`'s recorded `VERIFY-01 branch:` verdict

Do **not** re-derive the branch. Read the verdict Plan 39-02 recorded. Every rule below is a single
line with no leading or trailing whitespace.

### Branch A — apply when the verdict is `TRAVERSAL-CONFIRMED`

| Rule | Text |
|---|---|
| `listRule` | `@request.auth.id != "" && (boarder.user = @request.auth.id \|\| @request.auth.is_admin = true)` |
| `viewRule` | `@request.auth.id != "" && (boarder.user = @request.auth.id \|\| @request.auth.is_admin = true)` |
| `createRule` | `@request.auth.id != "" && (@request.body.boarder.user = @request.auth.id \|\| @request.auth.is_admin = true)` |
| `updateRule` | `@request.auth.id != "" && (boarder.user = @request.auth.id \|\| @request.auth.is_admin = true) && (@request.body.boarder:isset = false \|\| @request.body.boarder = boarder)` |
| `deleteRule` | `@request.auth.id != "" && (boarder.user = @request.auth.id \|\| @request.auth.is_admin = true)` |

### Branch B — apply when the verdict is `FALLBACK-REQUIRED`

Identical to Branch A on `listRule`, `viewRule`, `updateRule` and `deleteRule`. **Only `createRule`
changes**, per ROADMAP § Phase 39 criterion 1 — admin-bypass on create, ownership carried by the
list/view/update/delete traversal plus client-side boarder pinning:

| Rule | Text |
|---|---|
| `createRule` | `@request.auth.id != "" && (@request.auth.is_admin = true \|\| @request.body.recorded_by = @request.auth.id)` |

The recorder binding is kept on the fallback so attribution cannot be forged even though boarder
ownership is not server-bound. **PROJECT.md line 41's "denormalise the account id onto each payment"
fallback is superseded by D-39-06 — do not plan it, do not resurrect it as an option.** On Branch B,
SUBJ-05 becomes **partially client-only** (a hand-crafted non-admin create against another boarder
is not blocked server-side); that must be recorded as accepted threat T-39-03 and as a deviation,
and never described as server-enforced.

### Hard constraints on the text, either branch (carried invariants, non-negotiable)

- Never an empty string for a rule — PocketBase treats empty-string as **public**, not
  "unconfigured". Never `null` unless superuser-only is intended, which it is not here.
- Never the authenticated-caller conjunct **alone** on a write rule — that form is satisfiable by any
  authenticated user (PITFALLS #1; the real `isSuperUser = isLoggedIn` bug in
  `GiftExchangeManage.vue`). It appears here only as a guard alongside the ownership and admin
  branches, which is why the leading conjunct is correct and the bare form is still forbidden.
- Literal `is_admin` on every write branch. This project's admin is an ordinary `users` row with
  `is_admin = true`, **not** a PocketBase superuser — it is subject to every rule, so the explicit
  admin branch is load-bearing, not redundant.
- The dot-body accessor on `createRule`, never the deprecated dot-data form, which 403s on this
  instance.
- The `:isset` guard sits **outside** the admin OR-branch. Consequence, deliberate: **not even an
  admin can reassign a payment's boarder by editing it.** SUBJ-06 grants an admin create, edit and
  delete on any boarder's payments — editing *fields*, not moving a payment between boarders. Do not
  "helpfully" move the guard inside the admin branch.
- All five authored and pasted back **together**.
