## The status map the sweep asserts (confirmed against the official docs)

Assert **per operation**. Asserting 404 on a denied create, or 400 on a denied update, makes the probe
itself look broken and is the single easiest way to record a false result.

| Rule | Denial outcome |
|---|---|
| `listRule` | HTTP **200** with an empty items array and a zero total — **not** an error. This is the failure signature to watch for, and the reason every list case cross-checks against an admin-token count. |
| `createRule` | HTTP **400** |
| `viewRule` / `updateRule` / `deleteRule` | HTTP **404** |
| any rule set to `null` (superuser-only) hit by a non-superuser | HTTP **403** |

**The app admin is not a PocketBase superuser.** It is an ordinary `users` row whose `is_admin`
boolean is true, so it IS subject to every collection rule — which is exactly what makes the explicit
admin branch load-bearing rather than redundant. A true superuser bypasses all rules unconditionally,
so a sweep run with a superuser session would pass even against rules that had no admin branch at all.
Confirm which tier the supplied admin token belongs to before drawing any conclusion from the admin
half.
