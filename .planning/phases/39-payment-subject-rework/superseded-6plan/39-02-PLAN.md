39-04 reads to pick its rule text, plus four probe blocks and a proven revert.

## Candidate rule text under probe (spike window only)

Set **only these two** rules. Leave `listRule`, `viewRule` and `deleteRule` exactly as Plan 39-01
captured them — a partially-applied five-rule rewrite is PITFALLS Pitfall 6, and this spike is
deliberately not that rewrite.

| Rule | Candidate text for the spike window |
|---|---|
| `createRule` | `@request.auth.id != "" && (@request.body.boarder.user = @request.auth.id \|\| @request.auth.is_admin = true)` |
| `updateRule` | `@request.auth.id != "" && (boarder.user = @request.auth.id \|\| @request.auth.is_admin = true) && (@request.body.boarder:isset = false \|\| @request.body.boarder = boarder)` |

**Why the leading authenticated guard is load-bearing, not decoration.** For an unauthenticated
caller PocketBase evaluates `@request.auth.id` as the empty string, and `boarder.user` is the empty
string for 6 of the 7 live roster rows (`38-COLLECTION.md`). Without the leading
`@request.auth.id != ""` conjunct, the bare comparison `boarder.user = @request.auth.id` is
**empty-string-equals-empty-string, i.e. true**, and a tokenless caller would pass. Today's live
rules avoid this only because `paytime_payments.user` is `required: true` and therefore never empty
— the traversed field on the *related* collection is not. This is a new hole specific to the
traversal form, so Probe 4 exists to observe it directly. The guard is a conjunct alongside the
traversal and admin branches, **never a bare write rule on its own** — that bare form is the
PITFALLS #1 trap (satisfiable by any authenticated user) and is still forbidden.
